# 02C-1 · 反向寻光正确性与基准审计

> 基准 `afa0501`，工作分支 `fix/core-quality-audit`。本轮只做审计、参考工具与基准，**未修改生产搜索算法**。
> 参考扫描受步长限制，本文所有「漏报」结论都是「在 1 秒分辨率下未被发现」，不等于连续时间上的全局最优性证明。

## 1. 现有算法流程

```text
ReversePage.runSearch()
  └─ 逐本地日构造 DayRange[ startUtc, endUtc )
      └─ ReverseSearch.searchInRanges(goal, th, [range])      ← 同步调用，一天一次
          ├─ 粗扫：t = start; while t < end; t += 5 分钟
          │    pos = SolarCalc.position(t)
          │    if 双容差同时满足 → 细化
          │         refineAt ×3：±5min 内 30s → ±60s 内 5s → ±10s 内 1s（目标：最小 azErr+altErr）
          │         refined 点重新校验双容差；不满足则丢弃
          │         t += 10 分钟（跳过已细化区间）
          │    else t += 5 分钟
          ├─ 合并：按 UTC 排序，相邻间隔 ≤ 10 分钟的候选只保留 cost 较小者
          └─ 排序：按 azError+altError 升序；截断到 maxResults（页面传 30）
      └─ 汇总各日结果 → 全局按 cost 排序 → 截断 30
      └─ 每日结束后才：更新进度、写 Job、await nextFrame()、检查取消标志
```

关键事实（读自当前 HEAD 源码）：

| 常量/规则 | 值 | 位置 |
|---|---|---|
| 粗扫步长 | 300 000 ms | `ReverseSearch.ets:6` |
| 细化层级 | 30s / 5s / 1s，窗口 ±5min/±60s/±10s | `:8, :125-128` |
| 细化目标 | `cost = azError + altError` | `:78` |
| 命中判据 | `azError ≤ azTol && altError ≤ altTol` | `:84` |
| 命中后跳过 | 10 分钟 | `:139` |
| 合并阈值 | ≤ 10 分钟（贪心、保留较小 cost） | `:150-160` |
| 排序/截断 | cost 升序 → `slice(0, maxResults)` | `:163-169` |
| 页面取消检查 | 每天一次 | `ReversePage.ets:145` |

## 2. 已确认的实际缺陷

| 编号 | 缺陷 | 性质 |
|---|---|---|
| **D1** | 有效窗口短于粗扫步长且落在两个 5 分钟采样点之间时，**整窗漏报**（返回空） | 漏报 |
| **D2** | 细化最小化的是 `azErr+altErr`，而有效性要求两个容差**分别**成立：cost 最小的点可能单轴越界，导致候选被整体丢弃，连带丢掉原本有效的粗扫命中点 | 逻辑不一致（算术可证） |
| **D3** | 容差放宽后有效窗口很长，粗扫每次跳 10 分钟，相邻细化最优点相隔 > 10 分钟，**10 分钟合并失效 → 同一连续窗口产出多个重复候选** | 重复/冗余 |
| **D4** | Top-K 只按 cost 排序，**没有时间分布策略**；逐日 `maxResults` 上限 30，跨日去重不做；重复候选会挤占配额 | 排序语义 |
| **D5** | 取消只在**每天结束后**检查；单日搜索是同步的，取消延迟上界 = 单日搜索耗时 | 响应性 |
| **D6** | 10 分钟合并是「相邻贪心」，没有窗口身份概念；`Candidate` 只有一个时刻，无法表达「一段连续窗口」 | 模型不足 |

未观察到的情况（不能声称不存在）：「两个独立窗口被错误合并」（本轮 `wrongMerges = 0`）；
「细化落到无效点」在真实太阳轨迹上未复现（见 §5），仅算术上可证。

## 3. 每个缺陷的最小可复现输入

### D1（漏报）— 上海 2026-10-30 本地日

- 目标：取 `2026-10-29T16:02:30.000Z` 的真实太阳位置
  `az = 19.247°`、`alt = -71.479°`（上海 31.2304, 121.4737）
- 容差：`azTol = altTol = 0.2°`
- 独立参考（1 秒扫描）：窗口 `[1793289734000, 1793289766000]`，长 **32 秒**，窗口内 cost = 0
- 旧实现：`searchInRanges` 返回 **空数组**
- 原因：该窗口落在两个 5 分钟采样点（`16:00:00` 与 `16:05:00`）之间；两点都超出 0.2° 容差 → 不进入细化
- 已固化为用例：`defect_short_window_between_coarse_samples_is_missed`

### D2（细化逻辑不一致）— 算术反例

- `azTol = 0.5`、`altTol = 5`
- 点 P：`azErr = 0.40`、`altErr = 4.50` → 双容差都满足，`cost = 4.90`（有效）
- 点 Q：`azErr = 0.60`、`altErr = 0.10` → `azErr > azTol`（无效），但 `cost = 0.70`
- 细化取 cost 最小 → 选 Q → 校验失败 → `continue` 丢弃；P 的有效命中信息一并丢失
- 已固化为用例：`defect_cost_minimum_can_fall_outside_one_tolerance`

### D3（重复候选）— 上海 2026-10-30 本地日

- 目标：`t0 = 本地日 + k*30min + 2.5min` 的真实位置，容差 `6° / 6°`
- 参考：每天 49 个连续有效窗口
- 旧实现：tromso 55 个候选、shanghai 83 个候选（`dupCand = 34`、`38`）
- 原因：窗口长达数小时，粗扫跳 10 分钟，相邻细化最优点间隔 > 10 分钟 → 合并规则不生效
- 已固化为用例：`defect_wide_tolerance_produces_duplicate_candidates_for_one_window`

### D4（Top-K 语义）

- 14 天：收集 10 条 → 保留 10 条 → 涉及 10 个不同日期
- 365 天：收集 36 条 → 保留 30 条 → 涉及 30 个不同日期（`costRange 0 ~ 2.48°`）
- 逐日 `maxResults = 30` 在实测中**从未触顶**（单日最多 1–2 条），因此跨日配额不是瓶颈；
  但排序完全按 cost，重复候选（D3）越多，越会挤占真正不同的机会

### D5（取消延迟）

- 页面结构：`for (每天) { searchInRanges(单日)；更新进度；await nextFrame()；if (cancelRequested) break; }`
- 单日搜索在 Node 镜像上 0–1 ms（355–422 次 `position`），但**取消只能发生在两天之间**
- 结论：取消延迟上界 = 单日搜索耗时；若某日容差很宽、命中密集，细化次数上升，延迟随之线性增加

## 4. 独立参考扫描的实现与限制

工具：`tools/reverse-check/scan.mjs`（Node，仅审计用，不参与 App 运行）

- 自带一份 NOAA/Meeus 太阳位置实现（与 `SolarCalc` 同公式族，独立于 `ReverseSearch`）
- `referenceWindows(goal, start, end, stepMs=1000)`：按 1 秒步长扫描，双容差**分别**判定，
  把相邻有效点（间隔 ≤ 1s）归为同一窗口，输出 `{startUtc, endUtc, bestUtc, bestAz, bestAlt, bestCost}`
- `productionSearch(...)`：与 `searchInRanges` 同构的镜像（5 分钟粗扫 / 30s-5s-1s 细化 / 10 分钟合并 / cost 排序），
  用于统计 `position` 调用次数与复算漏报；**不参与生成参考期望值**
- `compare(...)`：计算窗口召回、误合并、重复候选、结果有效性、最优误差差距

限制（必须如实说明）：

1. 参考扫描是**有限分辨率**：任何短于 1 秒的窗口或恰好跨在采样点之间的极窄窗口都可能同样被漏掉；
2. 只在给定地点/日期/目标网格上抽样，**不能**据此证明连续时间上的全局最优性；
3. 位置实现是 JS 镜像而非 ArkTS 原函数，两者同公式族，理论上等价；真实设备上的一致性由设备侧用例覆盖。

前一天返回空、当天返回空 —— 属于 D1 在边界的表现，而非跨日重复。

## 7. 结果排序与 Top-K 语义

现状：**只有模式 A（最精确匹配）**。

- 排序键严格为 `azError + altError`，同分时顺序不稳定（`Array.sort` 稳定性依赖实现）；
- 逐日 `maxResults` 上限 30，跨日不去重、不做时间分布；
- 重复候选（D3）会占用列表名额，把真正不同的机会挤出 Top-K；
- 页面最终再截断到 30，等于「全局取 cost 最小的 30 条」。

模式 B（拍摄机会分布）需要的最小接口改动：

1. `Candidate` 增加窗口身份（`windowStartUtc` / `windowEndUtc`）或用独立 `ShootWindow` 模型承载；
2. 排序前先按窗口去重，再按日期/时段做配额（如每日本地日最多 N 条、每 2 小时最多 M 条）；
3. `searchInRanges` 返回窗口对象而非单点，页面再决定如何呈现。

建议 2C-2 仍以**准确匹配优先**，模式 B 作为可选策略，不得为了均匀分布牺牲结果正确性。

## 10. 2C-2 推荐算法方案与复杂度

**方案：阈值穿越包围 + 二分求根 + 窗口对象化（不做更密的等步长全扫）**

1. **粗扫只用于检测穿越**：2 分钟步长（≈720 点/日），对 `altErr - altTol`、`altErr + altTol`、
   `azErr - azTol`、`azErr + azTol` 四个函数检测符号变化（方位差按环形处理，在 0/360 处取两侧阈值）；
2. **二分求根**：每个包围区间二分 10–12 次（到 1–2 秒精度），得到窗口边界时刻；
3. **区间相交**：alt 合法区间 ∩ az 合法区间 → 一个或多个 `[startUtc, endUtc)`；
4. **窗口内取最优点**：窗口通常很短（秒级到分钟级），在窗口内用黄金分割或 1 秒扫描取 cost 最小点，
   并以**双容差分别校验**（修掉 D2）；
5. **窗口去重**：按窗口身份（相交或间隔 < 30 秒）合并，取代 10 分钟贪心（修掉 D3、D6）；
6. **边界处理**：穿越点必须夹在 `[startUtc, endUtc)` 内；二分区间天然满足。

复杂度（每天）：

| 步骤 | 调用次数 |
|---|---|
| 穿越检测（2 分钟） | ≈720 |
| 二分（最多 ~10 个穿越 × 12 次） | ≈120 |
| 窗口内寻优（≤ 5 个窗口 × 60 次） | ≈300 |
| 合计 | **≈1 150 次/日**（旧实现 ≈380 次/日，约 3 倍） |

为什么比 5 分钟粗扫可靠：任何**由阈值穿越界定**的窗口都会被检出并求出真实端点，
不再依赖「采样点恰好落进窗口」；短于 2 秒的窗口仍可能漏（明确写进限制），
但 1 秒级参考扫描下的漏报率可从当前的 0%–14% 提升到接近 100%（以 2C-2 实测为准）。

为什么不选另外两种：

- **「粗扫改 1 分钟」**：调用量 1440/日（约 3.8 倍），但**依然会漏** 20–60 秒级窗口
  （本轮实测 0.2° 容差窗口只有 32–114 秒），只是把漏报区间从 5 分钟缩到 1 分钟，问题性质没变；
- **「1 秒全量扫描 365 天」**：31.5M 次 `position`/年，按当前 110k 次 ≈ 22 ms 线性外推约 6.3 秒（Node），
  设备上会明显更慢，且取消粒度、内存都不可接受。

## 11. 2C-3 的多日排序与性能工作范围

- **排序**：模式 A（cost）为默认；模式 B（分布）作为可选，需窗口身份 + 配额；
- **去重**：跨日按窗口身份去重，替代逐日贪心合并；本地日边界（23/25/23.5/24.5 小时）必须参与判定；
- **配额**：移除逐日 `maxResults`，改为全局配额 + 可选的每日上限；
- **性能目标**：365 天在新算法下 ≤ 45 万次 `position`（≈4 倍当前 11 万），并在真机上测单日/整段耗时
  与取消延迟（目标：取消在 ≤ 100 ms 内生效，必要时应把「穿越检测」分段让出主线程）；
- **不做**：本轮不引入 Worker/多线程，先在 2C-2 证明算法正确性，再考虑 2C-3 的调度优化。
